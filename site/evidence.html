Evidence

What’s proven, and what isn’t

A design document can claim anything. This page separates what an automated test demonstrates from what was measured once by hand, and both of those from what is currently just specified.

Two of the five upstream assumptions turned out to be wrong, and the design changed rather than the finding being explained away.

On negative controls

Roughly half of these are tests that something fails. A trust prototype that only demonstrates the happy path proves nothing — the scripted demo includes 18 named attacks, each of which must be denied at a specific, pre-committed layer.

Tier two

Measured against a real mesh

Before the design leaned on any SAM behaviour, five spikes tested it against a running mesh — one control plane, one router, three nodes. Rather than reading the documentation, the source was read directly and then the behaviour was reproduced.

S-2 · the load-bearing one · PASSED

Node attenuation evaluates the caller’s labels

A peer attesting agent_id=42 received the full tool catalogue. A peer attesting 777 was refused before any payload was read. 

[Auth] AuthZ Denied 12D3KooWGRdG…:
  biscuit: verification failed:
  failed to verify check #1:
  check if label("erc8004.agent_id", "42")

Stronger than specified: it also gates the service catalogue, so a denied caller cannot even enumerate what a node offers.

S-1 · changed the design

The specified “primary path” does not exist

The specification described the broker supplying labels in the approve call. That mechanism is not in SAM. Labels are declared by the node (sam-node run --labels, and the flag is on run, not join) and attested by the admin at approval — approve takes an empty body.

The trust property is unchanged, since approval is still the gate. But §6.1.3 was wrong and was rewritten.

S-5 · changed the design

Caller identity never reaches a local service

sam-node forwards the raw stream to a locally spawned MCP service as a dumb-pipe proxy and discards the caller’s PeerID. The subprocess sees no SAM_* environment variables.

This promoted the Call Attestation from optional hardening to the only mechanism by which an inbound sidecar learns who called.

S-3 · better than assumed

Initiator-side verification exists

The spec had treated this as unavailable and deliberately did not rely on it. In fact call_remote_tool accepts a required_labels argument and fails closed. It is opt-in per call, so it is a genuine second layer rather than a default safety net.

A defect found, and reported upstream

Bootstrap enrollment cannot complete on current upstream: sam-node POSTs to /enroll/status while the server accepts only GET, so the request 405s forever. This was re-verified at upstream 674af93 before filing as google/sam#297. SATM does not fork SAM, so the one-line fix exists only in a local scratch clone used for spikes.

Tier three

Specified, but not yet proven

Corrections

Claims that were narrowed

Two statements in earlier drafts were overstated. Both were caught in review and made precise rather than quietly dropped.

Before

“The system fails closed”

Too broad to be true. Now stated in two tiers: asset-moving authorization fails closed unconditionally; everything else fails closed except within explicitly bounded, logged staleness windows.

Before

“L1 anchoring makes the audit trail tamper-proof”

Anchoring proves inclusion and post-anchor immutability. It does not stop a compromised broker omitting an entry before anchoring. Omission is detectable via counterparty receipts — not prevented.

Residual risk, stated rather than hidden

A compromised broker can deny service, admit an unbound peer to the mesh, and fabricate or omit evidence before anchoring. It cannot move assets — that requires on-chain authority it does not hold. This is recorded as accepted residual risk in the threat model rather than argued away.

How to check any of this yourself

Everything above is reproducible. CI runs three jobs on every push: unit tests under -race, a PostgreSQL service container, and a live-chain job that deploys the registries to Anvil and runs the integration suite against them. 

git clone https://github.com/yorkerhodes3/sovereign-agent-trust-mesh
cd sovereign-agent-trust-mesh

# contracts
cd contracts && forge test

# services
cd services && go test ./...

# the live-chain suite, including the revocation proof
anvil --port 8545 &
forge script script/DeployRegistries.s.sol --rpc-url http://127.0.0.1:8545 \
  --broadcast --private-key $PK
go test -tags integration ./...
